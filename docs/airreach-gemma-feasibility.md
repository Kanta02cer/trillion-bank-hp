## 3. 今の構成に「そのまま」載せられない理由

1. **大きさ**：モデル 2.6GB は関数の上限（250MB・Python 500MB）を超える。Large functions（Beta・5GB）が要り、このプロジェクトでは**環境変数の追加（本番設定の変更）**が要る。このプロジェクトが「新しいプロジェクト」として既定で対象かは**未確認**
2. **重みの置き場所**：今の配信は公開リポジトリのブランチに成果物を push する方式。2.6GB の重みは公開 Git に入れない方針で、GitHub も 100MB を超えるファイルを受け付けない。→ Vercel のビルド中にダウンロードして関数に含めるか、CI から `vercel deploy --prebuilt` で直接送る方式に変える必要がある
3. **依存のインストール**：今の配信は依存を入れない（`installCommand: null`・依存なしの package.json）。Python の関数として `litert-lm-api` を入れたときに Vercel のビルドで入るかは**未確認**
4. **メモリ**：重みと埋め込みをファイルからメモリマップで読むため、メモリの上限が小さいとファイルの読み直しが増える（下の Mac の実測で、空きメモリが少ないときに同じ文章が 5秒→110秒になった）。2GB でどうなるかは Linux で上限をかけて測る必要がある
5. **同時の要求**：Fluid compute は1つのインスタンスに複数の要求を入れる。生成は CPU を占有するので、1インスタンス1件に絞る必要がある（試作の関数は処理中なら 429）

## 4. 試作（`tools/airreach-gemma/`）

### FAQ の下書きの作り方と確かめ

1. 本文の前処理：制御文字・区切りの記号を外し、**AI への指示らしき文（「AI…指示…答えて」「これまでの指示を無視」など）を本文から外す**（根拠にも使わせない）
2. Gemma に、よく聞かれる8問と、本文に答えがある質問（最大2問）を JSON（スキーマで形を固定・余分なキー禁止）で答えさせる。各問に「根拠（本文からそのまま抜き出した部分）」を付けさせる
3. コードで1問ずつ確かめる（`validate_faq_item`）：
   - 根拠を本文の**文**に当てる（見出し・`<br>`・「Q./A.」は区切りとして扱う）。当たらなければ要確認
   - 当たった文と、その直後に続く**条件・注意の文**から、**本文そのままの答え**（`answer_from_source`）を組み立てる。同じ段落なら見出しの下か同じ語を含む文、**空行をはさむ場合は同じ見出しの節の中で「ただし・なお・※」で始まる文か同じ語を含む文**だけ（別の見出し・関係の無い文は混ぜない・最大3文）
   - Gemma の言い換え（`answer`）を、その文と照らす：
     - **対象**：質問の項目（営業時間・駐車場など）の語が根拠にあるか
     - **数字**：答えの数字が根拠にあるか／「A〜B」の幅が同じ並びか（20:00〜10:00 を通さない）／**具体的な対象と数字（幅なら開始と終了の両方）の組**が根拠でも同じか。対象は数字の直前の具体的な語（カラー・土日祝）で、「料金」「営業時間」のような一般的な語では救わない。答えに対象が無く、質問が値を聞いているときは質問の対象（「土日祝の営業時間は？」の 土日祝）で照合する
     - **無料/有料・必要/不要・肯定/否定**：答えの文（節）ごとに、いちばん近い根拠の文と比べる
     - **言い換えの照合**：答えの語（質問の言い直しを除く）の6割以上が根拠にあるか
     - **条件の省略**：根拠のうち、質問の主題に関わる「のみ・まで・ため・できません・ご遠慮」などを含む文の中身が答えに入っているか。「ディナーのみ」の「ディナー」のように条件の直前の語は必須
   - 全部通れば `status=site`、1つでも外れたら `needs_check`（答えは「【確認が必要】」にし、根拠の引用と本文そのままの答えは担当者の確認用に残す）
4. 出力は下書き。公開は既存の確認・承認の流れで行う（自動公開しない）

## 5. 実測

### Linux x86_64（Vercel の大きさに合わせた制限つきコンテナ）— 2026-10-06 実測

**これは Vercel での実動確認ではない**。GitHub Actions の標準ランナー（公開リポジトリ・無料・4 vCPU）で、docker の `--memory`/`--memory-swap`/`--cpus` で上限をかけた。CPU の種類・メモリの数え方・冷起動は Vercel と同じとは限らない。

- 条件：`litert-lm-api` 0.17.1・Python 3.12.15・Linux 6.17（x86_64・glibc 2.41）。モデル `gemma-4-E2B-it.litertlm` 2,588,147,712 バイト・sha256 `181938105e0eefd105961417e8da75903eacda102c4fce9ce90f50b97139a63c`。文脈 4,096 トークン・出力上限 2,000・temperature 0.2・top_k 20・top_p 0.9・seed 1・thinking なし。スレッド数＝CPU 数
- 測り方：各条件の前にホストのファイルのキャッシュを捨てる（冷えた状態）→ 読み込み → 短い本文・食堂（1,708文字）・歯科（2,120文字）・公開ページの FAQ を各2回（初回と連続）→ 要約の定型文。時間は `time.perf_counter`、メモリはホスト側の cgroup を2秒ごと（`memory.current`・`memory.peak`・`memory.stat` の anon/file・`oom_kill`）、OOM は `docker inspect` の `OOMKilled`
- 実行：run 37466297568（XNNPack の重みのキャッシュなし）・37467758798 と 37469652785（キャッシュを先に作り、読み取り専用で渡す）

| 要約「今月の言及率は18.8%、前月は31.3%」（実際は逆） | ok（通過） | 使わない：自由文に数字（数字は定型文で作る） |
| 要約「FAQを追加したため、引用率が25.0%になりました」 | ok（通過） | 使わない：自由文に数字・因果の言い方「ため」 |
| （2回目）カット 3,300円・カラー 7,700円 → 「カラーの料金は3,300円」 | site（通過） | needs_check：対象と数字の組が違う（カラー→3300） |
| （2回目）平日 10:00〜20:00・土日祝 10:00〜18:00 → 「土日祝は10:00〜20:00」 | site（通過） | needs_check：対象と数字の組が違う（土日祝→10:00〜20:00） |
| （2回目）【駐車場】無料／空行／ただし利用客のみ2時間まで → 「駐車場は無料です」 | site（通過・条件も拾わない） | needs_check：重要な条件の省略。本文そのままの答えに条件の文が入る |

定型文の要約の例（架空の集計データ）：
> 2026年9月のAIの回答に名前が出た割合（すべての AI）は 31.3%（16回答中5回答）でした。2026年8月の 18.8%（16回答中3回答）から 12.5ポイント上がりました。2026年9月のAIの回答で出典になった割合（ChatGPT（検索なし））は未計測です。数字の変化の理由（施策の効果など）は、この計測だけでは判断できません。

FAQ の例（架空の美容室・通過したもの）：
```json
{"question": "営業時間は何時から何時までですか？", "answer": "営業時間は10:00〜20:00（土日祝は9:00〜19:00）です。",
 "answer_from_source": "営業時間:10:00〜20:00(土日祝は9:00〜19:00)", "evidence": "営業時間:10:00〜20:00(土日祝は9:00〜19:00)", "status": "site"}
```
要確認に回った例（架空の食堂・アレルギー）：答え「アレルギーのあるお客様は、ご注文の前にスタッフにお知らせください。」→ 本文の次の文「同じ厨房で小麦・卵・乳を扱っているため、完全に取り除くことはできません。」を落としたため要確認。`answer_from_source` には両方の文が入り、担当者はそれを見て書ける。

## 7. 置き場所の選択肢と、Vercel で 4GB にする正しい手順

| 案 | どこで動くか | 必要な変更 | 向き・不向き |
|---|---|---|---|
| **A. AI 用の Vercel プロジェクトを別に作る** | Vercel Functions（サーバー） | プロジェクト作成・Large functions・Function CPU を Performance・CI からモデルごと `vercel deploy --prebuilt` | 今のサイト・API・配信に触れずに試せ、消せば戻る。**向くのは**：Linux の 4GB/2CPU で FAQ 1回が 300秒（延ばしても 800秒）に収まり、OOM が無いとき。1件ずつの処理・冷起動の読み込み（2.6GB）が毎回の待ち時間に乗る |
| B. 今のプロジェクトに足す | Vercel Functions | 本番の環境変数・配信の仕組みの変更 | サイト全体のデプロイに影響。勧めない |
| C. ブラウザで動かす | **利用者の端末**（サーバーではない） | ページに LiteRT-LM の JS（Early Preview）など | 初回に約2.0GB のダウンロード、WebGPU が要る、画面を閉じると止まる。サーバーで動いたことにはならない |
| D. AI 用のサーバーを別に用意（VPS など） | 別のサーバー | 契約・費用・運用 | **向くのは**：Linux の 2GB/4GB で遅すぎる・OOM のとき、または常に読み込み済みにして待ち時間を短くしたいとき。メモリ 4〜8GB のサーバーなら、メモリマップの読み直しの心配が小さい |

Linux の実測（5）からの判断：
- **A（AI 用の Vercel プロジェクト）は試す価値がある**。条件は ① Function CPU を **Performance（4GB/2vCPU）** にする（Standard の 2GB では OOM）② **XNNPack の重みのキャッシュを作ってモデルと一緒に関数に入れる**（関数の場所は読み取り専用で、実行時に作れない。モデル 2.6GB＋キャッシュ 0.79GB＋ランタイム≒3.4GB＝Large functions の 5GB 以内）③ 1インスタンス1件ずつ。FAQ 1回は 37〜72秒（Linux・2CPU）で、既定の 300秒に収まる
- 未確認の危険：キャッシュのファイル名にモデルのファイルの情報（数字）が入っており、ビルドしたときと Vercel の実行環境で同じファイルとして扱われるか（扱われないと作り直そうとして失敗し、メモリが 3GB を超える）／2.6GB＋0.8GB の関数の冷起動の時間／Vercel のメモリの数え方（ファイルの読み込み分を上限に数えるか）
- **D（別サーバー）**は、A で冷起動が長すぎる・キャッシュが効かない場合の代わり。メモリ 4GB 以上（余裕を見て 8GB）・常に読み込み済みにできる

**Vercel で関数を 4GB / 2vCPU にする手順（公式：https://vercel.com/docs/functions/configuring-functions/memory）**
- Fluid compute では `vercel.json` の `memory` でメモリを決められない（書くとビルドで警告が出る）。前の版の「`vercel.json` に `memory: 4096`」は誤り
1. （A の場合）AI 用の新しいプロジェクトを作る。今の `trillion-bank-hp` の設定は変えない
2. そのプロジェクトの **Settings → Functions → Advanced Settings → Function CPU** で **Performance（4GB / 2vCPU）** を選ぶ（Pro 以上。プロジェクトの全関数の既定になる）
3. **新しくデプロイし直す**（設定は以後のデプロイにだけ効く）
4. **Deployments → 対象のデプロイ → Resources** で関数を開き（Observability）、関数名の横の情報アイコンでメモリが 4GB になっていることを確かめる
5. 実行時間は `vercel.json` の `functions` の `maxDuration`（Pro 最大 800秒）で決める。Large functions は新しいプロジェクトなら既定で対象（既存は環境変数 `VERCEL_SUPPORT_LARGE_FUNCTIONS=1`）

**費用の目安（推定・Vercel では測っていない）**：iad1 の単価（Active CPU $0.128/時間・メモリ $0.0106/GB時間）で、生成中に CPU を使い切るとして、4GB/2vCPU は1秒あたり約 $0.0000829。Linux の実測の FAQ 1回 37〜72秒なら **1回 約 $0.003〜0.006（約0.5〜1円）**。冷起動の読み込みの時間・その費用は未測定。
